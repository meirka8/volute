# Wire fixtures

Interaction blobs exactly as the Claude Code harness wrote them.

- `v2.1.260-basic/` and `edge-cases/` are from the shipped cvc 0.7.0 binary. `v2.1.260-basic/` was ingested from the repo's public synthetic transcript `cvc-core/tests/fixtures/claude-code/v2.1.260/basic.jsonl`; `edge-cases/` from one synthetic transcript written for these tests (redaction markers, truncation, a server-side tool, unanswered tool calls).
- `cvc-0.7.1-server-tools/` is from the harness with the change for issue #134, which records a server-side tool call (`server:<name>`) with `tool_protocol` `server` and the status its result block reported; 0.7.0 recorded `native` and `failure` for every one of them (Design.md §10.5, "Server-side tools"). The files were produced by that patched harness from synthetic transcripts: `8fc40ad6…` (seven server-side calls, four successes and three failures, and a Read) and its follow-up `94705671…` from `cvc-core/tests/fixtures/claude-code/v2.1.300/server-tools.jsonl`, and `0d3a13e0…`, the edge-case step above recorded again, so it has the same id as the file in `edge-cases/`. Both files are kept: the old one is what a 0.7.0 capture of the step looks like (the search is `native` and `failure`, shown as "server-side · result not recorded"), the new one what a capture records now (the search is `server` and `success`).
- `cvc-0.7.1-stimulus-v2/` is from the harness with the change for issue #133 (version 2 of the stimulus encoding): every part of a node's `user_prompt` (a person's words, a subagent's task, injected context, a compaction summary, each tool result) starts with a marker that carries a boundary token, which a reader verifies against the node's own id (`../../lib/stimulusV2.ts`). Twenty steps of one synthetic session, produced by that patched harness (an unreleased build, printed as cvc 0.7.0, with that change and no other) from synthetic transcripts: the edge-case transcript that `edge-cases/` was written from (redaction markers, truncation, a person typing while tools ran, forged markers in tool output, a step whose response, reasoning and a call's arguments could not be scrubbed, the first step of a subagent, a compaction summary, a result whose call is not known) and the server-side tools transcript. Eight of the steps have the id of a step in `edge-cases/` or `cvc-0.7.1-server-tools/`, recorded again, so the old and the new encoding of one step can be read side by side; the other twelve are new. They hold the real shapes of the change as the harness wrote them when this folder was made, and may be refreshed if a later change to the producer alters them (the capture's record of calls it left out of a step, and the stand-in for a response it withheld, are not in these files: the tests build both from their documented shapes).

The only edit is that local paths were replaced by `/work/repo`; files are named `<fixture>/<interaction id>.json` and are kept byte for byte, so do not reformat them.
They hold no real data: the only address is `fixture@example.invalid`, and redacted values appear only as `[CVC_REDACTED:v1:...]` markers (and a boundary token such as `~cvc-0000000000000000`, which one node's tool output spells on purpose, to imitate a marker). The one temp-looking path is `/tmp/notes.txt` in `cvc-0.7.1-server-tools/8fc40ad6…` and in the same step in `cvc-0.7.1-stimulus-v2/`: a path inside the provider's code-execution sandbox, written into the synthetic transcript, not a path on any machine. `../wireNodes.test.tsx` allows that string in those two files and nothing else of its kind.
`../wireNodes.test.tsx` loads every file in this directory, so a new file needs an entry there; `../wireNodes.v2.test.tsx` holds the files of `cvc-0.7.1-stimulus-v2/` to what is particular to them.
