# Volute CVC v0.5.0

Volute CVC v0.5.0 adds **linked Git worktree support across every component**. CVC now works from any checkout of a repository — `git worktree add` checkouts included — with one shared private store per repository and capture attribution per worktree. This release is aimed squarely at parallel, agent-driven workflows where several tasks proceed simultaneously in sibling worktrees of the same repository.

CVC keeps **explicitly available AI-assisted development context** alongside Git history. It records only information exposed or supplied by its integrations; it neither retrieves hidden chain-of-thought nor promises a verbatim record of a black-box model's internal reasoning.

[Full Changelog](https://github.com/meirka8/volute/compare/v0.4.2...v0.5.0)

## Highlights

- **Linked worktrees are fully supported** by the CLI, MCP server, language server, and VS Code extension. The database, privacy/consent state, locks, and rewrite state live in `$(git rev-parse --git-common-dir)/cvc` and are shared by all worktrees of a repository; `.thoughtignore`, context resolution, and branch state remain local to each active worktree. Hooks resolve through Git's effective hooks path, and every entry point discovers the repository layout fail-closed — malformed worktree metadata is rejected rather than mistaken for a normal repository.
- **Automatic linking is scoped to the capturing worktree.** Every capture records a local-only fingerprint of its active worktree, and the post-commit linker considers only thoughts captured in the committing worktree. Parallel checkouts can no longer claim each other's floating thoughts, either temporally or through a shared conversation. Rows captured before this release keep their historical eligibility.
- **The MCP server binds to one repository and worktree at startup** and rejects cross-repository or sibling-worktree targets on every call, with filesystem-identity revalidation. One agent per worktree, one binding per server process.
- **Redaction plans are portable across worktrees.** New plans use a v2 repository identity derived from the canonical common Git directory; historical v1 plans remain readable with their original, deliberately worktree-bound semantics. Plan files are now read with symlink, size, and duplicate/unknown-field rejection.
- **VS Code extension hardening.** The extension requires a trusted workspace, ignores workspace-scoped binary path settings (a repository's `.vscode/settings.json` can no longer select the binaries the extension launches), binds exactly one repository folder per session, discovers repositories through VS Code's trusted Git binary, and launches CLI actions as argument-vector tasks instead of shell text.

## Included components

- `cvc-core` — Rust library for local storage, Git integration, policy enforcement, linking, and sync data structures.
- `cvc-cli` — the `cvc` command-line interface.
- `cvc-mcp` — MCP server for explicitly submitted interaction records and local history access.
- `cvc-lsp` — language server used by editor integrations.
- `cvc-plugin` — VS Code extension for the supported local VS Code chat-session workflow.
- `cvc-reviewer` — client-side React reviewer for GitHub-hosted CVC data.
- `@volute_cvc/cvc-mcp` — npm launcher for released CVC binaries.

## Install

### GitHub release assets

Once the full release workflow completes, download an archive and `SHA256SUMS.txt` from the [v0.5.0 GitHub release](https://github.com/meirka8/volute/releases/tag/v0.5.0). Verify the archive against that manifest **before** extracting it, then put `cvc` (or `cvc.exe`) on `PATH`. Each archive includes `cvc`, `cvc-mcp`, and `cvc-lsp`.

| Platform | Archive |
| --- | --- |
| Linux x86-64 | `cvc-x86_64-unknown-linux-gnu.tar.gz` |
| macOS x86-64 | `cvc-x86_64-apple-darwin.tar.gz` |
| macOS ARM64 | `cvc-aarch64-apple-darwin.tar.gz` |
| Windows x86-64 | `cvc-x86_64-pc-windows-msvc.zip` |

Expected additional release assets are `LICENSE`, `THIRD-PARTY-NOTICES.md`, `install.sh`, and `install.ps1`. Each native archive and VSIX also includes the mechanically generated third-party notice file. The standalone installer assets default to v0.5.0, select the matching supported archive, and verify its checksum; set `CVC_RELEASE_VERSION` to an explicit valid release tag to override that version. Review a script before running it.

From any Git working tree — a primary checkout or a linked worktree — get started with:

```bash
cvc init
cvc status
```

### VS Code Marketplace

After the full release workflow completes, [Volute CVC (`volute.cvc`)](https://marketplace.visualstudio.com/items?itemName=volute.cvc) is expected to be available from the VS Code Marketplace. The extension supports VS Code `^1.91.0` and uses the platform-specific bundled language server.

### npm MCP launcher

After the full release workflow completes, the [@volute_cvc/cvc-mcp](https://www.npmjs.com/package/@volute_cvc/cvc-mcp) launcher is expected to be available from npm:

```bash
npm install --global @volute_cvc/cvc-mcp@0.5.0
```

It provides `cvc-mcp` and `cvc`, downloads the matching release binary on first use, and verifies it against the release checksum manifest. Configure `cvc-mcp` in your MCP client as documented in the [MCP setup guide](https://github.com/meirka8/volute/blob/v0.5.0/cvc-mcp/README.md).

## Upgrade notes

- **The local database migrates additively on first open.** A new nullable column records each capture's worktree origin. The migration is safe for mixed-version use: v0.4.2 binaries can still read and write a migrated database, and captures they write behave like pre-upgrade rows.
- **The sync wire format is unchanged.** v0.5.0 reads formats v1–v5 and writes v5, byte-identical to v0.4.2 output; the worktree fingerprint is local-only and never projected. Cross-version push/pull interoperability is unaffected.
- **`cvc run` now refuses to run inside a bare repository** instead of executing the command without capture. Run it from a worktree.
- **The MCP server must be started inside a repository worktree.** It no longer creates state relative to an arbitrary working directory, and requests targeting a different repository or a sibling worktree fail with an explicit error.
- **The VS Code extension is inert in untrusted workspaces and multi-root workspaces** (one repository folder per window is the supported mode), and machine-scoped binary path settings are now the only settings it honors for binary selection.
- Capture acknowledgement, sharing consent, and auto-push remain per-repository CLI TTY challenges; linked worktrees share the repository's consent state. No consent boundary changed in this release.

## Privacy and sharing

CVC is **local-first, not local-only**. Captures live under the repository's common Git directory in `cvc/` and are private by default; linked worktrees share that private store. Remote publication is a separate, explicit action: sharing and sync can publish selected data through Git, while authentication and component-management commands can also use the network.

Review content before sharing and protect access to the repository and its common Git directory. Built-in scrubbing and `.thoughtignore` are defense in depth, not a guarantee: they can miss credentials, personal data, encoded values, or provider-specific formats. Once published to Git, content may remain in objects, clones, forks, reflogs, caches, and backups. Rotate an exposed credential first; local deletion and tombstones are suppression mechanisms, not guaranteed physical erasure.

## Release security and hardening

- Release tags must exactly match the Rust, VS Code extension, and npm package versions before publishing.
- Release archives include a SHA-256 manifest; the installer and npm launcher verify the selected archive and reject unsafe redirects or archive members.
- The workflow pins its GitHub Actions by full immutable Git object SHA, uses scoped job permissions, and will publish GitHub build provenance attestations for workflow assets. After downloading an asset, verify its provenance with GitHub CLI: `gh attestation verify <asset> --repo meirka8/volute`.
- npm publishing is configured to use npm trusted publishing.

The same-release SHA-256 checksums are corruption/integrity checks, not independent signatures: because the archive and manifest are both hosted in the same GitHub release, they do not independently protect against a compromised release account. Download only from this repository and review installers before running them.

## Known limitations

- **Linux ARM64 is not released.** The shell installer, PowerShell installer, and npm launcher support the same platform matrix and reject unsupported platforms before downloading an asset.
- **Sharing is explicit.** Capture acknowledgement, destination sharing consent, conversation sharing, manual publication, and auto-push are distinct consent boundaries. Auto-push is off by default.
- **Exact squash relinking expects a range to be observed from one worktree.** Observing the same range from two different worktrees can create ambiguous evidence that conservatively blocks exact relinking for that range ([#39](https://github.com/meirka8/volute/issues/39)); the affected thoughts remain floating rather than mislinked.
- **Very high concurrent capture volume can hit database lock contention.** Simultaneous captures from many parallel worktrees may surface visible, fail-closed capture errors under contention ([#40](https://github.com/meirka8/volute/issues/40)).
- **Hosted Reviewer requires deployment configuration.** The default Reviewer mode is local PAT mode. Hosted Reviewer integration works only when a deployment explicitly sets `VITE_HOSTED_MODE=true` and provides `VITE_PLATFORM_API_URL`.
